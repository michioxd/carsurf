# CarSurf — TODO

Open items, newest and most urgent first. Sources: roadmap "Way out", memory notes, and the 2026-08-16 device audit.

## Fixed (2026-08-16, build 0.1.4-27) — user-verified on the CarPlay screen

- **Fresh-enable live-sync without the reload.** Enable/disable now mutates `DBApplicationController` in place (`_loadApplicationWithInfo:` / `_removeApplicationWithBundleIdentifier:`) and fires `_didAddApplications:` / `_didRemoveApplications:` — the grid re-renders live with **no** `FBSApplicationLibrary` invalidation, **no** screen reflow, **no** alphabetical re-sort. Verified on the Simulator (7245D718) and confirmed on-screen by the user via UI toggles after a userspace restart: 15 in-place events, 0 `unrecognized selector` / `EXC_BAD_ACCESS` / PAC, CarPlay on one pid throughout.
- **The `carPlayDeclaration` crash.** `_updatePolicyForApplication:` sends `carPlayDeclaration` to the `DBApplication`, which does not implement it (only its `-info`, a `DBApplicationInfo`, does). A guarded `class_addMethod` bridge forwards it to `-[DBApplicationInfo carPlayDeclaration]` — the declaration the runtime-admission factory built. The `class_getInstanceMethod` guard keeps native behavior if the system ever provides it. (Deliberate, documented exception to CSRuntime's "never class_addMethod" rule: the framework sends this selector and crashes when it is absent.)
- **The roster-rebuild reload is retired for toggles.** `CSDeltaNeedsRosterRebuild` removed; whole-library invalidation now only happens on genuine uninstall.
- **Config-to-scene reactivity audit.** The app-side CarPlay gate now reads the current allowlist instead of caching its launch-time value, and a live CarPlay scene exits when the global or per-app toggle is turned off. Phone-only app processes are not terminated. Still verify the teardown timing once on a connected vehicle.

## Crashes (top priority)

- [x] **PAC crash — improved, pending a connected-car test.** Synthetic roster entries are pinned alive (`gPinnedRosterInfos`), and the in-place path pins the `DBApplicationInfo` + `DBApplication` it loads. No crash in Simulator toggle testing. Still needs a LYNK&CO connected-car run to confirm.
- [x] **CRS fetch interception crash — reproduced on the CarPlay Simulator.** Launchd recorded `CarPlayApp` `SIGSEGV` in the native `DBIconLayoutVehicleDataProvider getIconStateWithCompletion:` path while the CRS fetch wrapper was installed. Disabling that wrapper stopped the startup/Customize crash; keep the fetch hook off until a non-reconstructing read path is designed.
- [ ] **Enabled-app launch crash — root cause found, fix built (0.1.4-27-17+debug), pending on-screen tap verification.** Toggling any enabled app off→on and then launching it from the CarPlay grid aborted the CarPlay host (`SIGABRT` + respawn: "suddenly disappear and re-show") while the launched app process stayed alive. `CSCrashDiag` captured the reasons: `-[DBApplication applicationIdentity]` and `-[DBApplication processIdentity]` *unrecognized selector* (`carPlayDeclaration` was the first of the family, already bridged). **Root cause:** the in-place re-enable path (`_loadApplicationWithInfo:` → `_didAddApplications:`) leaves the icon backed by a thin `DBApplication` *wrapper* that re-exposes only `-info`/`-bundleIdentifier`/`-appPolicy`/BOOL getters; DashBoard's policy/launch/scene code sends it the full `FBSApplicationInfo` identity family (`applicationIdentity`/`processIdentity`/`signerIdentity`/`carPlayDeclaration`), all of which live on `-info`. A full reload doesn't crash because the native startup pipeline (`allInstalledApplications`) processes each app completely and caches its launch identity, so the tap never re-queries the wrapper. **Fix:** one `-forwardingTargetForSelector:` on `DBApplication` (replacing the per-selector `carPlayDeclaration`/`applicationIdentity` bridges) forwards any selector the wrapper lacks but its `-info` answers to `-info`. It does not change `-respondsToSelector:` (stays NO), so native feature-detection is untouched. Confirmed loaded and stable on iPhone 11 (CarPlay pid 44637); awaiting a physical icon-tap to close.
- [x] **Customize-empty-on-relaunch** — DashBoard's *own* `setIconState` can write an empty `pages[0]` during startup. CarSurf now restores the same vehicle's persisted `*-CarDisplayIconState.plist` into native CRS icon objects when a fresh process has no in-memory snapshot, then keeps the native writer call coherent. The previous in-memory last-good fallback remains for later transient empties.

- [x] **Icon flicker on re-enable (disable→re-enable oscillation) — FIXED (0.1.4-27-18+debug), device-verified.** After re-enabling an app the icon appeared then repeatedly disappeared/reappeared for ~1 minute: the disable and the following re-enable each started a `CSVerifyHiddenDeltaAfterDelay` chain carrying a **frozen** delta, and the stale disable chain kept replaying `hiding` while the enable chain replayed `un-hiding` across attempts 1–4. Fix: each reassertion now prunes its frozen delta against the **live** enabled set (`CSRuntimeEnabledIdentifierSet`) at fire time and stops the chain when a newer toggle has superseded everything it was defending (`reassertion superseded by a newer toggle, chain stopped`). Reconcile defense for a plain single disable is preserved (`CSVerifyHiddenDeltaAfterDelay` is still needed — DashBoard reconciles hidden writes back to all-visible on reconnect/customize). Verified on iPhone 11 (vehicle 7245D718): rapid toggles produce only the supersede line, no `hiding`/`un-hiding` ping-pong, no visible flicker.

## Scene bridge

- [ ] **`multiScene=0`** — `UIApplicationSceneManifest` is missing on iOS 18.5, so the multi-scene hooks never install; only single-scene bridging works.
- [ ] **First scene after re-enable ignores the display setting — parked (not currently reproducible, 2026-08-17).** When an app is re-enabled and opened for the first time, its CarPlay scene does not follow the configured per-app interface/aspect (e.g. "horizontal iPad"); it comes up with a default geometry. Closing the app from the iPhone (scene teardown) then reopening, or disconnecting/reconnecting CarPlay, brings up the correct geometry. Investigation notes:
  - Geometry is applied **once**, from `CSCarSceneConnected` → `CSApplyScaleToCarScene`, fired on `UISceneDidActivateNotification` and **guarded by a `seen` set keyed on `scene.session.persistentIdentifier`** (`apptweak/CSSceneBridge.m` ~L365). So a scene that activates before its `coordinateSpace.bounds` is final gets measured once and is **never re-applied** for that session — a strong candidate for the wrong first geometry. A fresh process (close+reopen) or reconnect makes a new session → re-measures correctly.
  - Options themselves are read fresh per connect (`optionsForBundle:` at L328), but the **idiom** is cached per-process via `dispatch_once` in `CSTraits` (`CSOptionsForThisApp`); if it is first queried before config load, the app builds phone-idiom UI for the whole process.
  - Fix ideas: also re-apply geometry on a later signal (scene `didUpdateCoordinateSpace` / first layout pass / a one-shot next-runloop retry) instead of only the first activation; and/or don't cache the idiom for the process lifetime.
  - Note on logging: runtime-admitted Apple apps (Stocks/YouTube) are sandboxed and cannot write the shared `carsurf.log`, so their app-side `scene`/`traits` lines land in the app **container** `tmp/carsurf.log`, not the shared log — that is why the shared log shows app-side tags only for less-sandboxed apps (ChargeLimiter, TrollStore). Grab the container log (or a visual check) on the next repro.
